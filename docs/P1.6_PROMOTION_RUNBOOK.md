## 2. Precondiciones Obligatorias (Preflight Checklist)

Antes de iniciar cualquier ventana de mantenimiento o intento de promoción en un consumidor real, deben satisfacerse las siguientes condiciones:

1. **Estado del Consumidor Limpio:**
   - El árbol de trabajo de Git del consumidor debe estar en estado limpio o documentado.
   - La dependencia actual en `package.json` debe señalar a `openmemory@0.3.1`.
2. **Ausencia de Bloqueos:**
   - El archivo `.promotion.lock` NO debe existir en el directorio del consumidor.
   - Si existe, verificar con `isProcessAlive` que el PID no esté en ejecución y que la edad del archivo no exceda el TTL (60s).
3. **Quiescencia Absoluta de Bases de Datos SQLite:**
   - Ninguna base de datos (`*.db`, `*.sqlite`, `*.sqlite3`) en la raíz o subdirectorios (`.openmemory/storage/`) debe tener archivos `*-wal` con tamaño mayor a 0 bytes.
   - No debe existir ningún archivo `*-shm` (memoria compartida activa que indica escritores o lectores en proceso).
4. **Integridad Criptográfica del Tarball Candidato:**
   - El archivo `openmemory-0.3.14-rc4.tgz` debe existir en `.work/artifacts/` y su hash SHA-256 debe coincidir con `af88fae90107dfda797c7f6bcc982cf6bbd7ef53fd9a5d887c9bf77185a35f6e`.
5. **Espacio en Disco:** Mínimo 500 MB libres para alojar el backup transaccional y el área de staging.

## 3. Protocolo de Ejecución Paso a Paso

### Fase 0: Adquisición de Bloqueo Exclusivo (Locking Atómico)
* **Comando interno:** `engine.acquireLock()`
* **Acción:** Crea `.promotion.lock` utilizando la bandera atómica `{ flag: 'wx' }` (O_CREAT | O_EXCL). Registra `operationId`, `pid`, `token` criptográfico, `acquiredAt` y `expiresAt`.
* **Criterio de éxito:** Lock creado en disco; token almacenado en memoria.

### Fase 1: Verificación de Preflight y Catálogo de Estado
* **Comando interno:** `engine.verifyPreflight()`
* **Acción:**
  1. Valida el tamaño y hash SHA-256 del tarball.
  2. Ejecuta `scanSqliteQuiescence()` recursivamente.
  3. Indexa los archivos de configuración del consumidor (`package.json`, `package-lock.json`).
* **Criterio de éxito:** Tarball validado; 0 archivos WAL/SHM activos; estado transicional a `PREFLIGHT_VERIFIED`.

### Fase 2: Creación del Backup Transaccional y Manifiesto Forense
* **Comando interno:** `engine.createTransactionalBackup()`
* **Acción:**
  1. Crea `backups/backup_<operationId>/`.
  2. Copia recursivamente `.openmemory/` preservando dotfiles, carpetas vacías y permisos POSIX (`copyDirectoryRecursive`).
  3. Copia `package.json` a `package.json.bak` y calcula su hash SHA-256.
  4. Copia `package-lock.json` a `package-lock.json.bak` (si existe).
  5. Genera y persiste `operation_manifest.json` con el catálogo criptográfico completo.
* **Criterio de éxito:** Directorio de backup completo, manifest persistido con estado `BACKED_UP`.

### Fase 3: Aplicación de la Instalación
* **Comando interno:** `engine.applyInstallation()`
* **Acción:** Ejecuta `npm install "<tarballPath>" --save-exact` con un límite estricto de `timeout: 180000` (3 minutos).
* **Verificación:** Comprueba que `node_modules/openmemory/package.json` reporte versión `0.3.14-rc4`.
* **Criterio de éxito:** Instalación finalizada con código 0 y versión confirmada.

### Fase 4: Smoke Test de Solo Lectura con Prueba de Cero Mutaciones
* **Comando interno:** `engine.executeSmokeTest()`
* **Acción:**
  1. Captura una instantánea del sistema de archivos del consumidor antes del test.
  2. Inicializa el motor de OpenMemory y valida las exportaciones del paquete.
  3. Ejecuta el smoke test de las 29 herramientas MCP verificando contratos de esquema.
  4. Compara el estado del disco posterior al test con la instantánea previa.
* **Criterio de éxito:** 0 mutaciones en archivos de datos, 29 herramientas MCP cargadas exitosamente.

### Fase 5: Post-Verificación y Compromiso Transaccional (Commit)
* **Comando interno:** `engine.executePostVerification()`
* **Acción:** Si se configuró comparador de auditoría (`npm audit`), valida ausencia de regresiones de severidad.
* **Compromiso:** Actualiza `operation_manifest.json` a estado `COMMITTED`, registra timestamp y libera el lock `.promotion.lock`.
* **Criterio de éxito:** Estado `COMMITTED` alcanzado; lock liberado limpiamente.

## 4. Criterios de Aborto y Manejo de Errores

La promoción se aborta inmediatamente en cualquiera de las siguientes circunstancias:
1. Discrepancia en el hash SHA-256 del tarball candidato.
2. Detección de cualquier archivo WAL con tamaño > 0 o archivo SHM activo.
3. Fallo en la adquisición o pérdida de posesión del lock (`assertLockHeld`).
4. Fallo o timeout (> 180s) durante el comando `npm install`.
5. Error durante el smoke test o detección de mutaciones en datos persistentes del consumidor.
6. Recepción de señales de interrupción (`SIGINT`, `SIGTERM`).

---

## 5. Procedimiento de Rollback Verificado (Reversión Transaccional)

Ante cualquier fallo o invocación explícita de aborto, el motor ejecuta `executeRollback()`:

1. **Captura Forense Inmediata:**
   - Escribe `promotion_abort_evidence.json` en la raíz del consumidor conteniendo el motivo del aborto, el estado fallido y la traza de ejecución.
2. **Restauración en Staging Aislado:**
   - Crea un directorio temporal `.staging-rollback-<opId>`.
   - Copia el contenido de `.openmemory/` desde `backups/backup_<opId>/openmemory/` al staging.
   - Comprueba criptográficamente cada archivo en staging contra el catálogo previo en `operation_manifest.json`.
3. **Intercambio Atómico Seguro (Swap with Rescue):**
   - Renombra el directorio `.openmemory/` activo a `.live-swap-<opId>`.
   - Renombra `.staging-rollback-<opId>` a `.openmemory/`.
   - *Mecanismo de Rescate:* Si el segundo renombrado falla, el motor rescata inmediatamente `.live-swap` de vuelta a `.openmemory`.
   - Tras el intercambio exitoso, elimina el directorio temporal de swap.
4. **Restauración de Configuración de Paquetes:**
   - Restaura `package.json` desde `package.json.bak`.
   - Restaura o elimina `package-lock.json` según correspondía en el estado inicial.
   - Ejecuta `npm install openmemory@0.3.1 --save-exact` con timeout de 180s.
5. **Verificación Bidireccional de Paridad:**
   - Audita `.openmemory/` restaurado: número exacto de archivos, tamaños, permisos y hashes SHA-256 idénticos al estado pre-promoción. Cero archivos huérfanos.
6. **Liberación del Lock:**
   - Se libera `.promotion.lock` y se actualiza el manifiesto a `ROLLED_BACK`.

### Manejo de Doble Falla (Doble-Fault Recovery):
Si el propio procedimiento de rollback falla de manera crítica:
* El área de staging dañada se renombra automáticamente a `.quarantined-staging-<opId>-<timestamp>` para evitar pérdidas o sobrescrituras.
* La traza del error de rollback se persiste en `promotion_abort_evidence.json`.
* El backup original en `backups/backup_<opId>/` permanece 100% inalterado para restauración forense asistida.

---

## 6. Criterios para Declarar la Recuperación Exitosa

Se declara que una recuperación por rollback ha sido exitosa únicamente cuando:
* La versión instalada en `node_modules/openmemory/package.json` es `0.3.1`.
* El hash de las bases de datos SQLite coincide exactamente con su hash inicial.
* Todos los archivos en `.openmemory/` coinciden bit a bit con el inventario inicial.
* Cero bloqueos huérfanos en disco.
* El archivo `promotion_abort_evidence.json` registra claramente el estado y la causa del aborto.
