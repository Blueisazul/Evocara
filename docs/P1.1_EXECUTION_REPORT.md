## 3. Prioridad 2 — CI Reproducible y Matriz de Compatibilidad

### 3.1 Política Arquitectónica sobre `package-lock.json`
Se investigó la ausencia de un `package-lock.json` versionado en Git:
* **Hallazgo:** El archivo `.gitignore` incluye explícitamente `package-lock.json` y `bun.lockb`. En el entorno local existe un archivo `package-lock.json` desactualizado con versión `0.3.2`.
* **Análisis Arquitectónico:**
  1. *OpenMemory es una biblioteca / framework reutilizable:* En el ecosistema npm, las bibliotecas distribuyen su `package.json`; `package-lock.json` nunca se publica en el tarball de distribución (npm lo excluye automáticamente). Los consumidores de la biblioteca resuelven sus dependencias contra las restricciones semver de `package.json`.
  2. *Riesgo en CI:* Si el repositorio no versiona lockfile, `npm install` en CI resuelve contra las versiones más recientes disponibles en el registro npm dentro del rango semver (`^`). Si una dependencia ascendente (e.g., `@modelcontextprotocol/sdk`, `zod`) introduce una regresión, el CI podría fallar inesperadamente.
  3. *Solución Implementada y Coherente:* El workflow de GitHub Actions (`.github/workflows/ci.yml`) fue endurecido con detección condicional:
     ```bash
     if [ -f package-lock.json ]; then
       echo "Installing via npm ci (lockfile detected)..."
       npm ci
     else
       echo "Installing via npm install (no lockfile in checkout)..."
       npm install
     fi
     ```
  4. *Consecuencia Documentada:* Mantener `package-lock.json` fuera del control de versiones previene conflictos de fusión continuos entre ramas de desarrollo divergentes (`fix/v0.3.0-contract-closure`, `feat/consumer-ready-integration`), pero requiere que el CI verifique la compilación y pruebas ante las dependencias resueltas. Las dependencias en `package.json` mantienen rangos semver compatibles.

### 3.2 Matriz Multiplataforma (9 Jobs)

## 4. Prioridad 3 — Seguridad y Pruebas Adversariales

Se auditaron las implementaciones que gobiernan los bloqueos, persistencia, contención de rutas, rollback, cuarentena y promoción:

### 4.1 Recuperación de Locks y Condiciones de Carrera
* **Mecanismo:** La persistencia utiliza `fs.writeFileSync(lockPath, payload, { flag: 'wx' })` para adquisición atómica exclusiva a nivel del sistema operativo.
* **Recuperación Atómica:** Para evitar condiciones de carrera al liberar o reclamar un lock huérfano, el motor utiliza un renombre previo atómico (`fs.renameSync(lockPath, tempGarbagePath)`) antes de eliminar el archivo físico (`fs.unlinkSync`). Esto impide que un proceso concurrente cree un nuevo lock legítimo justo en el milisegundo en que otro proceso detecta y borra un lock vencido.

### 4.2 Identidad del Propietario, Tokens y Expiración
* Al adquirir un lock mediante `tryAcquireLockDetailed`, se genera un token criptográfico único (`tok_<agentId>_<timestamp>_<uuid>`).
* La liberación con `releaseLockDetailed` requiere coincidencia del token. Si un agente no autorizado intenta liberar el lock sin el token, la operación es rechazada (`PASS 2` en `INVARIANTS-P10`).

### 4.3 PIDs Muertos y Reutilización de PID (PID Reuse)
* **Investigación:** La función `isProcessDead(pid)` comprueba la vida del proceso mediante `process.kill(pid, 0)`. Si el proceso no existe, el sistema operativo retorna `ESRCH`, confirmando que el proceso murió.
* **Escenario de Reutilización de PID (PID Reuse):** Si el sistema operativo reasigna el mismo PID a un proceso no relacionado, `process.kill(pid, 0)` retornará `false` (el proceso parece "vivo").
* **Mitigación Implementada y Verificada:** El motor aplica una condición compuesta:
  ```typescript
  const deadProcess = isProcessDead(lockData.pid);
  if ((exp !== undefined && exp <= now) || deadProcess) {
    isStale = true;
  }
  ```
* **Prueba Adversarial Añadida (P1.1):** Se incorporaron dos subpruebas específicas en `test-p10-adversarial-invariants.js`:
  1. *Subtest 1.3:* Lock con PID vivo (simulando reutilización de PID) pero con TTL no expirado. La adquisición por un nuevo agente fue **estrictamente bloqueada** (el lock no fue robado prematuramente).
  2. *Subtest 1.4:* Lock con PID vivo pero con TTL expirado. El lock fue **recuperado de forma atómica y segura** tan pronto venció el TTL.

### 4.4 Contención de Rutas en Windows, Symlinks y Junctions
* La función `resolveSecurePath` resuelve rutas normalizadas, verifica la pertenencia léxica al directorio raíz permitido y bloquea intentos de escape (`..`, barras invertidas, secuencias nulas).
* En Windows, se probó la creación de *junctions* hacia áreas restringidas; cualquier resolución que atraviese un enlace simbólico o junction hacia el exterior es interceptada con `Symlink traversal violation` o `Path traversal violation`.

### 4.5 Detección Bidireccional de Modificaciones y Prevención de Archivos Rebeldes
* En el Gate 5 del protocolo de rollback, la verificación no se limita a comprobar que los archivos originales existen: se realiza una verificación inversa de conteo e inventario SHA-256.
* La prueba `INVARIANTS-P10` Test 6 demostró que la inyección de un archivo no autorizado posterior a un rollback simulado dispara inmediatamente una excepción `POST_ROLLBACK_COUNT_MISMATCH`.

### 4.6 Cuarentena Segura de Artefactos Corruptos
* El motor de recuperación transaccional (`BackupManager`) nunca destruye directorios de recuperación que contengan manifiestos sintácticamente inválidos. En su lugar, los traslada a un espacio de cuarentena (`.quarantined-*`) para su posterior análisis forense, preservando la evidencia al 100%.
