## 1. Resumen Ejecutivo de la Auditoría de CI

El archivo de workflow `.github/workflows/ci.yml` define el pipeline automatizado de integración continua, pruebas multiplataforma y generación de atestaciones de procedencia SLSA (Supply-chain Levels for Software Artifacts) para OpenMemory.

Durante la Misión P1.6 se realizó una auditoría profunda de este archivo bajo el principio de tratar la configuración de CI como **código de producción crítico**. Se identificaron y corrigieron riesgos de elevación de privilegios, carreras en la generación de atestaciones dentro de matrices y falta de fijación inmutable de dependencias de actions.

---

## 2. Hallazgos de Seguridad y Reestructuración del Workflow

### 1. Principio de Menor Privilegio (Least Privilege)
* **Estado en P1.5:** Los permisos `id-token: write` y `attestations: write` estaban declarados en la raíz del workflow (`top-level permissions`). Esto otorgaba credenciales OIDC de alto privilegio a cada uno de los 9 runners de prueba de la matriz, exponiendo tokens criptográficos innecesariamente durante suites de prueba o en pull requests.
* **Corrección P1.6:**
  - El nivel superior del workflow se configuró estrictamente con `permissions: contents: read`.
  - El job de pruebas `test` tiene exclusivamente `permissions: contents: read`.
  - Los permisos `id-token: write` y `attestations: write` se aislaron de manera estricta en un nuevo job independiente: `release-attestation`.

### 2. Eliminación de Carreras en la Generación de Atestaciones
* **Estado en P1.5:** El paso `actions/attest-build-provenance` se ejecutaba dentro de la matriz de 9 runners (`matrix.os` x `matrix.node-version`), lo que significaba que 9 runners concurrentes intentaban emitir atestaciones separadas y potencialmente divergentes para el mismo tarball en Sigstore/Rekor.
* **Corrección P1.6:** Se desacopló la atestación de la matriz. La atestación ahora reside en un job dedicado `release-attestation` que:
  1. Depende del éxito completo de todos los runners de prueba (`needs: test`).
  2. Se ejecuta en un único runner canónico (`ubuntu-latest`) con Node 22.x LTS.
  3. Se activa exclusivamente en eventos de `push` a ramas autorizadas (`main`, `master`) o creación de tags oficiales (`v*`), quedando totalmente desactivado para pull requests.

### 3. Fijación Inmutable de Actions (Action Pinning a Commit SHA)
* **Estado en P1.5:** Las actions estaban referenciadas mediante tags flotantes mayores (`@v4`, `@v2`). Si la cuenta de un mantenedor de action es comprometida o un tag es reubicado, el pipeline podría ejecutar código malicioso.
* **Corrección P1.6:** Todas las actions de GitHub fueron fijadas a sus hashes de commit SHA inmutables con comentarios semánticos de versión:
  - `actions/checkout@11bd71901bbe5b1630ceea73d27597364c9af683 # v4.2.2`
  - `actions/setup-node@39370e3970a6d050c480ffad4ff0ed4d3fdee5af # v4.1.0`
  - `actions/upload-artifact@b4b15b8c7c6ac21ea08fcf65892d2ee8f75cf882 # v4.4.3`
  - `actions/attest-build-provenance@c074443f1a5fb4aee83904b71123799736ad970e # v2.2.0`

### 4. Límites de Tiempo y Gestión de Concurrencia
* Se configuró `timeout-minutes: 25` en el job `test` y `timeout-minutes: 15` en `release-attestation` para prevenir el consumo descontrolado de minutos de cómputo ante deadlocks.
* Se configuró `concurrency` con `cancel-in-progress: true` agrupado por workflow y referencia Git para cancelar automáticamente ejecuciones redundantes sobre commits superados.

## 3. Matriz Multiplataforma y Compatibilidad de Node.js

La matriz contempla 9 combinaciones de ejecución:
* **Sistemas Operativos:** `ubuntu-latest`, `windows-latest`, `macos-latest`.
* **Versiones de Node.js:** `18.x`, `20.x`, `22.x`.

### Evaluación del Soporte de Node.js 18:
* **Estado Oficial de Node.js:** Node.js 18 (Hydrogen LTS) alcanzó su fin de ciclo de vida (*End-of-Life*) el 30 de abril de 2025 y ya no recibe parches de seguridad de la Node Foundation.
* **Decisión Técnica en OpenMemory:** Se mantiene Node 18 dentro de la matriz de CI para verificar retrocompatibilidad con consumidores empresariales que aún no han completado su migración a Node 20 o 22.
* **Compatibilidad de Dependencias:** El paquete en producción (`dependencies: @modelcontextprotocol/sdk, zod`) no impone restricciones incompatibles con Node 18. La advertencia `EBADENGINE` detectada en `ini@7.0.0` está restringida a `devDependencies` (`@opencode-ai/plugin`) y no impide la ejecución de las suites de prueba en Node 18.

## 4. Requisitos y Condiciones para Atestación de Procedencia SLSA

Para que la atestación SLSA v0.2 emitida por Sigstore/Rekor sea auténtica y verificable:
1. **Entorno de Ejecución:** Debe ejecutarse obligatoriamente dentro de un runner oficial de GitHub Actions (los entornos locales no poseen el token OIDC provisto por GitHub).
2. **Identidad OIDC:** GitHub emite un token de identidad de corta duración que certifica la URL del repositorio, el commit SHA exacto y el workflow que generó el artefacto.
3. **Firma Criptográfica:** El runner de GitHub firma el digest SHA-256 del tarball (`openmemory-*.tgz`) y publica la transparencia en Rekor sin necesidad de gestionar claves privadas permanentes.
4. **Verificación Externa:** Cualquier consumidor puede verificar la atestación descargada mediante:
   ```bash
   gh attestation verify openmemory-0.3.14-rc4.tgz --owner Blueisazul
   ```
