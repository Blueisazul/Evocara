## 1. Executive Summary

This audit evaluates the complete Continuous Integration (CI) architecture and release engineering pipeline for OpenMemory. It addresses the 9-runner multiplatform matrix, GitHub Actions security posture (least privilege, SHA pinning, OIDC isolation), lockfile versioning and packaging reproducibility, and Node.js runtime support tiers.

### Key Audit Findings:
1. **Matrix Coverage:** 9 distinct execution contexts (Ubuntu 24.04, Windows Server 2025, macOS 14/15 × Node.js 18.x, 20.x, 22.x).
2. **Action Pinning & OpenSSF Scorecard:** All external GitHub Actions are pinned to full 40-character immutable commit SHAs with inline version comments.
3. **Least Privilege & OIDC Isolation:** Top-level permissions default to `contents: read`. The `test` job operates strictly with `contents: read`. The `release-attestation` job is isolated, gated by the successful completion of `test`, restricted to protected push events/tags, and granted OIDC token and attestation permissions only when needed.
4. **Lockfile Resolution:** Synchronizing and committing `package-lock.json` solves CI non-determinism without affecting npm package distribution, because npm ignores `package-lock.json` by spec during `npm pack`.
5. **Node.js 18 Support Tier Distinction:** Node 18 reached official upstream End-of-Life (EOL) on April 30, 2025. Runtime execution of OpenMemory core is 100% verified on Node 18 (zero runtime dependencies), but upstream devDependency toolchain warnings (`ini@7.0.0` requiring `>=22.22.2`) are documented as non-fatal dev-time constraints.

## 3. GitHub Actions Security & Supply Chain Hardening

### 3.1 Immutable SHA Pinning Audit

Every external GitHub Action used across the CI and attestation jobs is pinned to an immutable 40-character commit SHA:

```yaml
# actions/checkout
uses: actions/checkout@11bd71901bbe5b1630ceea73d27597364c9af683 # v4.2.2

# actions/setup-node
uses: actions/setup-node@39370e3970a6d050c480ffad4ff0ed4d3fdee5af # v4.1.0

# actions/upload-artifact
uses: actions/upload-artifact@b4b15b8c7c6ac21ea08fcf65892d2ee8f75cf882 # v4.4.3

# actions/attest-build-provenance
uses: actions/attest-build-provenance@c074443f1a5fb4aee83904b71123799736ad970e # v2.2.0
```

**Security Impact:** Prevents supply chain compromise via compromised mutable tags (`v4`, `v4.2.2`). Even if an upstream tag is maliciously altered or deleted, the runner executes the exact cryptographic Git tree audited.

### 3.2 Granular Permissions Matrix

| Context | Permissions Defined | Principle Enforced |
| :--- | :--- | :--- |
| **Workflow Top-Level** | `permissions: contents: read` | Deny-by-default; prevents ambient token leakage. |
| **`test` Job** | `permissions: contents: read` | Zero write capabilities; test suites cannot mutate repository or mint tokens. |
| **`release-attestation` Job** | `permissions: contents: read`, `id-token: write`, `attestations: write` | OIDC token writing restricted exclusively to post-validation attestation job. |

## 4. Lockfile Reproducibility Investigation & Resolution

### 4.1 Historical Problem in P1.6
In P1.6, `package-lock.json` was kept in `.gitignore` due to concerns that committing it might alter the published package contents, while omitting it resulted in divergent transitive dependency resolution across different CI runners and Node versions.

### 4.2 Empirical Investigation & Verification
1. **npm Pack Specification:**
   According to npm packaging rules, `package-lock.json` is automatically and unconditionally excluded from the tarball created by `npm pack` when publishing libraries.
2. **Empirical Verification:**
   * Package verification run without `package-lock.json`: 69 entries, unpacked size 862,135 bytes, tarball SHA-256 `af88fae90107dfda797c7f6bcc982cf6bbd7ef53fd9a5d887c9bf77185a35f6e`.
   * Package verification run with `package-lock.json` present and versioned: exactly 69 entries, unpacked size 862,135 bytes, tarball SHA-256 `af88fae90107dfda797c7f6bcc982cf6bbd7ef53fd9a5d887c9bf77185a35f6e`.
3. **Reproducibility Verdict:**
   Committing `package-lock.json` produces **zero changes** in the published npm artifact while enabling `npm ci` across all CI runners for deterministic, hermetic dependency installation.

## 5. Node.js 18 Support Tier & Upstream Constraints

### 5.1 End-of-Life (EOL) Reality
* **Node.js 18 (Hydrogen):** Initial release October 2022. Upstream EOL was reached on April 30, 2025. Node.js no longer issues security patches for Node 18.
* **Node.js 20 (Iron):** Active LTS until October 2024, Maintenance LTS until April 2026.
* **Node.js 22 (Jod):** Active LTS until October 2025, Maintenance LTS until April 2027.

### 5.2 Transitive DevDependency Engine Warning
During dependency installation on Node.js 18 and Node.js 20 (<22.22.2), npm issues:
```text
npm WARN EBADENGINE Unsupported engine {
npm WARN EBADENGINE   package: 'ini@7.0.0',
npm WARN EBADENGINE   required: { node: '>=22.22.2' },
npm WARN EBADENGINE   current: { node: 'v18.20.7' }
npm WARN EBADENGINE }
```
**Audit Analysis:**
* `ini@7.0.0` is introduced solely as a deep transitive dependency of the developer tool `@opencode-ai/plugin` (`@opencode-ai/plugin -> effect -> ini`).
* OpenMemory itself has **zero runtime dependencies** (`"dependencies": {}`).
* The compiled JavaScript in `dist/` relies exclusively on Node.js built-ins (`fs`, `path`, `crypto`, `events`, `child_process`).
* Therefore, consumer applications running Node.js 18 execute OpenMemory with 100% operational fidelity and zero engine warnings upon installation.

## 6. Supply Chain Attestation & SLSA Provenance Architecture

The `release-attestation` job is architected with strict conditional gating:

```yaml
if: github.event_name == 'push' && (github.ref == 'refs/heads/main' || github.ref == 'refs/heads/master' || startsWith(github.ref, 'refs/tags/v'))
```

1. **Precondition Gating:** It requires the entire 9-matrix `test` job to succeed (`needs: test`). If any runner fails on any OS or Node version, attestation is skipped.
2. **Branch Protection:** Attestation cannot trigger on arbitrary branches or fork pull requests.
3. **Cryptographic Identity:** Uses GitHub OIDC (`actions/attest-build-provenance`) backed by Sigstore transparency logs to bind the build runner, commit SHA, and artifact hash into a tamper-evident SLSA v0.2 provenance bundle.
