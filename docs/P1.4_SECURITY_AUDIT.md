## 1. Resumen de Hallazgos y Vulnerabilidades Mitigadas

Durante la revisión adversarial de seguridad independiente realizada en P1.4, se detectaron y remediaron 5 debilidades en el motor transaccional:

### 1.1 Fuga por Directorio Intermedio Simbólico (Intermediate Symlink Bypass)
- **Vulnerabilidad:** `isContainedWithin` validaba `realpathSync` únicamente si el archivo objetivo (`resolvedTarget`) existía físicamente. Si el objetivo no existía aún (por ejemplo, al crear un archivo dentro de una ruta en staging), solo se aplicaba la comprobación léxica `path.relative`. Si un directorio intermedio era un symlink apuntando a una ruta externa (ej. `/app/link_dir -> /etc`), la creación de `/app/link_dir/new_file` escapaba de la contención.
- **Remediación:** Se implementó una resolución ascendente del ancestro existente más cercano (`while (ancestor) { if (existsSync) realpathSync(ancestor) ... }`), garantizando que cualquier enlace simbólico o junction en la cadena de directorios intermedios sea detectado y bloqueado antes de crear el archivo.

### 1.2 Condición de Carrera TOCTOU en `releaseLock()`
- **Vulnerabilidad:** `releaseLock` abría y leía `.promotion.lock`, validaba `token === this.lockToken`, y posteriormente eliminaba el archivo. En sistemas concurrentes de alta carga, si el lock expiraba o era reclamado justo en ese intervalo por otro proceso, el proceso anterior eliminaba el lock legítimo del nuevo proceso.
- **Remediación:** Se implementó un protocolo de renombrado atómico previo (`fs.renameSync(lock, tempGarbage)`). Tras el renombrado, se valida el token dentro de `tempGarbage`. Si el token coincide con `this.lockToken`, se elimina definitivamente; si no coincide, el lock pertenece a otro proceso y se restaura inmediatamente (`fs.renameSync(tempGarbage, lock)`).

### 1.3 Bloqueo Permanente por Archivo de Lock Corrupto o de 0 Bytes
- **Vulnerabilidad:** Si el proceso anterior terminaba abruptamente en el momento exacto de crear `.promotion.lock`, dejando un archivo vacío de 0 bytes o con JSON corrupto, `JSON.parse` fallaba silenciosamente y el lock no se reclamaba, lanzando un error no capturado `EEXIST` que bloqueaba todas las operaciones posteriores.
- **Remediación:** Se implementó detección explícita de archivos vacíos o JSON inválido (`isCorrupted`), permitiendo la reclamación segura si la antigüedad del archivo supera el TTL o si el archivo está corrupto.

### 1.4 Preservación de Modos de Permisos de Archivo (`chmod`)
- **Vulnerabilidad:** `copyDirectoryRecursive` utilizaba `fs.copyFileSync`, el cual no preserva los bits de permisos ejecutables (`0o755`) en entornos POSIX (Linux / macOS).
- **Remediación:** Se incorporó `fs.chmodSync(dstPath, stat.mode)` para garantizar 100% de fidelidad de permisos en respaldos y restauraciones multiplataforma.

### 1.5 Robustez del CLI y Parámetros
- **Vulnerabilidad:** El CLI no soportaba el alias `--consumer` ni `--help`, y no validaba si `--consumer-path` existía en disco antes de comenzar.
- **Remediación:** Se añadió soporte para `--consumer`, `--help`, validación de existencia de directorio y validación numérica estricta de `--expected-size`.

## 2. Suite de Regresión Adversarial (HARDENING-P14)

Se diseñó la suite `.work/experiments/test-p14-engine-security-hardening.js` con 10 escenarios:
1. **TEST 1:** Detección de symlink intermedio en archivo objetivo inexistente (PASS).
2. **TEST 2:** Detección de colisión de prefijos (ej. `app` vs `app-evil`) y límites de unidad (PASS).
3. **TEST 3:** Auto-reclamación de lock corrupto de 0 bytes (PASS).
4. **TEST 4:** Exclusión mutua ante colisión concurrente con error estructurado (PASS).
5. **TEST 5:** Liberación segura contra TOCTOU preservando locks foráneos (PASS).
6. **TEST 6:** Preservación de permisos y modo de archivo cross-platform (PASS).
7. **TEST 7:** Validación del CLI: `--help`, `--consumer`, rutas inexistentes y tamaños inválidos (PASS).
8. **TEST 8:** Rescate del directorio vivo ante fallo de swap en staging (PASS).
9. **TEST 9:** Persistencia completa de evidencia forense y stack trace ante fallo de rollback (PASS).
10. **TEST 10:** Idempotencia en invocaciones repetidas de rollback (PASS).

**Resultado:** **10/10 escenarios aprobados (100%) en 253ms.**
