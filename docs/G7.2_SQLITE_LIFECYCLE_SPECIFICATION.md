## 1. Contexto y Objetivos

En arquitecturas multi-agente basadas en persistencia local SQLite en modo WAL (`Write-Ahead Logging`), la gestión del ciclo de vida de las bases de datos, la consolidación atómica del log de transacciones y la observabilidad continua representan fronteras críticas de resiliencia.

Esta especificación consolida tres pilares arquitectónicos introducidos en OpenMemory G7.2 / G8:

1. **Gestión del Ciclo de Vida y Checkpointing Seguro de SQLite:** Abstracción explícita (`SQLiteLifecycleManager`) que administra conexiones registradas, realiza descubrimiento recursivo seguro de bases de datos en workspace y ejecuta `PRAGMA wal_checkpoint(TRUNCATE)` coordinado con locks mutuos, sin eliminación manual de archivos auxiliares (`-wal`, `-shm`).
2. **Coordinador Periódico de Salud (`DiagnosticHealthCoordinator`):** Planificador con ciclo de vida explícito (`start()`, `stop()`), no invasivo, strictly read-only (`repair: false`), protegido contra solapamientos y tolerante a excepciones para evitar la terminación abrupta del proceso anfitrión.
3. **Auditoría y Endurecimiento de Seguridad (Security Hardening):**
   - Eliminación de falsos positivos en la detección de actividad SQLite (clasificación precisa del archivo `-shm` de memoria compartida).
   - Detección de orfandad por muerte de procesos (`isProcessDead(pid)`) y protección contra reciclado de PIDs mediante cota máxima de retención (5 minutos).
   - Prevención de condiciones de carrera TOCTOU en la reclamación de locks y exclusión estricta de symlinks externos y directorios voluminosos (`node_modules`, `dist`, `.work`).

## 2. Bloque A — Arquitectura del Ciclo de Vida SQLite

### 2.1 Inventario de Conexiones y Bases Administradas

OpenMemory distingue estrictamente entre:
- **Bases de datos administradas (`ManagedSQLiteDatabase`):** Registradas explícitamente mediante `registerDatabase(dbPath, name, dbInstance?)`. Tienen metadatos de ciclo de vida, trazabilidad de checkpoints anteriores y control directo.
- **Bases de datos del workspace (`Workspace Discoverable Databases`):** Archivos `.db` o `.sqlite` detectados durante escaneos controlados que no pertenezcan a directorios excluidos ni enlaces simbólicos externos.

```
                    +------------------------------------+
                    |        StorageEngine Facade        |
                    +------------------------------------+
                                      |
                      +---------------+---------------+
                      |                               |
        +----------------------------+  +----------------------------+
        |   SQLiteLifecycleManager   |  | DiagnosticHealthCoordinator|
        +----------------------------+  +----------------------------+
                      |                               |
       +--------------+--------------+                | (Read-Only)
       |                             |                v
+-------------+              +---------------+  +--------------------+
| Managed DBs |              | Workspace DBs |  | runDiagnostics()   |
| (Registry)  |              |  (Discovery)  |  +--------------------+
+-------------+              +---------------+
       |                             |
       +--------------+--------------+
                      |
                      v
       +-----------------------------+
       | PRAGMA wal_checkpoint(...) |
       | - Mutex Lock Coordination   |
       | - Zero Manual Unlinks       |
       | - Deterministic Result Parse|
       +-----------------------------+
```

### 2.2 Semántica de `PRAGMA wal_checkpoint(TRUNCATE)`

La consolidación del WAL se ejecuta de forma segura siguiendo estas reglas deterministas:
1. **Adquisición de Lock Mutuo:** Se coordina mediante `withStateLock` con la clave `sqlite-maint-${hash}` para garantizar exclusión mutua frente a operaciones concurrentes de mantenimiento o migraciones.
2. **Ejecución del Pragma:** Se emite `PRAGMA wal_checkpoint(TRUNCATE)` sobre la conexión activa o mediante una conexión temporal abierta estrictamente para el mantenimiento.
3. **Interpretación Estricta de Resultados:**
   - La respuesta nativa de SQLite es una fila con `{ busy: number, log: number, checkpointed: number }`.
   - Si `busy !== 0`, se reporta deterministamente como `success: false, busy: true, error: "Checkpoint incomplete: active SQLite readers or writers held database lock"`. **Bajo ninguna circunstancia se considera satisfactorio un checkpoint marcado como busy.**
   - En modo `TRUNCATE`, el éxito exige `busy === 0` y que el tamaño físico del archivo `-wal` tras el checkpoint sea exactamente `0` bytes (o que se hayan consolidado todas las páginas pendientes).
4. **Prohibición de Borrado Manual:** Jamás se utiliza `fs.unlinkSync` sobre archivos `-wal` o `-shm` para forzar la consolidación. SQLite gestiona internamente la sincronización física de memoria compartida y páginas de disco.

## 3. Bloque B — Coordinador Periódico de Salud (`DiagnosticHealthCoordinator`)

### 3.1 Contrato de Configuración

```typescript
export interface HealthCoordinatorConfig {
  intervalMs?: number;        // Intervalo entre ciclos (defecto: 60,000 ms, min: 1,000 ms)
  enabled?: boolean;           // Flag de activación (defecto: true)
  alertThrottleMs?: number;   // Limitador de alertas recurrentes (defecto: 300,000 ms)
  rootDir?: string;           // Directorio raíz opcional para escaneo
  onStatusChange?: (newStatus: string, oldStatus: string | null, report: DiagnosticReport) => void;
  onCheckCompleted?: (report: DiagnosticReport) => void;
  onError?: (error: Error) => void;
}
```

### 3.2 Invariantes de Operación y Seguridad
1. **Strictly Read-Only:** Los ciclos periódicos invocan `runDiagnostics({ repair: false })`. No se ejecutan reparaciones automáticas, cuarentenas ni mutaciones destructivas en segundo plano.
2. **Prevención de Solapamiento (`Anti-Overlap Guard`):** Mediante el flag `isExecuting`, si un ciclo de diagnóstico se prolonga más que el intervalo configurado, los ticks subsiguientes se omiten de forma segura, incrementando la métrica `totalSkippedDueToOverlap` sin apilar temporizadores en el event loop.
3. **Aislamiento Total de Excepciones:** Si un subsistema lanza una excepción durante el diagnóstico, el coordinador captura el error, incrementa `totalFailures`, emite un evento de telemetría `health.coordinator_exception` y notifica al hook `onError` sin provocar la caída del proceso anfitrión.
4. **Ciclo de Vida Limpio y `unref()`:**
   - El temporizador se programa con `timer.unref()`, evitando que el planificador mantenga colgado el proceso de Node.js al finalizar las tareas principales.
   - El método `stop()` limpia el timer de forma determinista y transiciona el estado a `running: false`.
5. **Cero Timers Globales Ocultos:** La importación de módulos no arranca ningún proceso en segundo plano. El coordinador debe ser instanciado e iniciado explícitamente (`storage.startHealthCoordinator()`).

## 4. Bloque C — Auditoría y Endurecimiento de Seguridad

### 4.1 Clasificación de Quiescencia SQLite sin Falsos Positivos de `-shm`

**Defecto Preexistente:** En implementaciones previas, la existencia del archivo `.db-shm` se evaluaba como `active = true`, clasificando erróneamente cualquier base de datos cerrada como "activa con transacciones no consolidadas".  
**Comportamiento Real del Motor SQLite:** En modo WAL, SQLite crea el índice de memoria compartida `-shm` (típicamente 32 KB). Tras cerrar las conexiones o tras un checkpoint completo, el archivo `-shm` puede permanecer en el sistema de archivos sin lectores ni escritores activos.  
**Mitigación Implementada:** La auditoría en `StorageEngine.auditWorkspaceSQLite` evalúa ahora:
- Una base es activa únicamente si existe `.db-wal` y su tamaño en disco es estrictamente superior a `0` bytes (`walStat.size > 0`).
- La presencia aislada de `.db-shm` con `-wal` de 0 bytes o inexistente se clasifica correctamente como estado **QUIESCENT**.

### 4.2 Endurecimiento de Advisory Locks

1. **Detección de Procesos Muertos (`isProcessDead`):**
   - `PersistenceEngine.inspectLocks()` comprueba ahora `isProcessDead(lockData.pid)` mediante el envío de señal nula `process.kill(pid, 0)`.
   - Si el proceso propietario no existe (`ESRCH`), el lock se clasifica inmediatamente como `isStale: true, deadProcess: true, isLocked: false`, independientemente de que su TTL futuro aún no haya expirado.
2. **Defensa contra Reutilización de PIDs (`PID Recycling Defense`):**
   - Se establece una antigüedad máxima admisible (`maxAgeExceeded = now - acquiredAt > 300,000 ms`). Incluso si el sistema operativo reutiliza un PID, un lock con más de 5 minutos de retención es considerado obsoleto.
3. **Resiliencia TOCTOU en Limpieza Concurrente:**
   - En `cleanupStaleLocks`, la eliminación física de locks está protegida con bloques `try/catch`, absorbiendo condiciones de carrera donde múltiples procesos concurrentes intentan desvincular el mismo archivo obsoleto simultáneamente.

### 4.3 Contención de Rutas y Enlaces Simbólicos en Escaneo de Workspace

En `auditWorkspaceSQLite`:
- Se utiliza `fs.lstatSync(fullPath)` en lugar de `fs.statSync`.
- Si `stat.isSymbolicLink()` es verdadero, la entrada se omite inmediatamente, impidiendo ataques de evasión de directorio o bucles infinitos por enlaces simbólicos cíclicos.
- Se excluyen directorios no relevantes o de alto volumen: `node_modules`, `.git`, `backups`, `scratch`, `dist`, `.work`, `.turbo`, `.next`.

## 5. Integración en CLI y Protocolo MCP

### 5.1 Comandos CLI
- `openmemory sqlite checkpoint [dbPath] [--mode TRUNCATE|FULL|PASSIVE|RESTART] [--json]`: Ejecuta checkpoint sobre una base individual o sobre todas las bases detectadas en el workspace.

### 5.2 Herramientas MCP
- `openmemory_sqlite_checkpoint`:
  - Parámetros: `dbPath` (string opcional), `mode` (enum opcional: TRUNCATE, FULL, PASSIVE, RESTART).
  - Retorna el reporte estructurado de mantenimiento con bytes consolidados y estado de contención.
